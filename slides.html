A real-time alarm correlation, semantic SOP retrieval, and human-in-the-loop remediation for a chemical batch plant

The control room problem

A 24/7 batch plant generates hundreds of alarms per shift. When something goes wrong, operators face:

  • Alarm floods — the same root cause fires 3–10 individual alarms
  • SOP sprawl — procedures scattered across binders, shared drives, PDFs
  • Lost tribal knowledge — "what did we do last time?" lives in people's heads
  • Time pressure — thermal excursions, cavitation, dosing faults compound in seconds

The ask

Turn plant data into real-time situational awareness: group related alarms, surface the right SOP, remember how operators resolved it before, and propose a structured remediation — with a human still in control.

Our Demo: Four processes, one knowledge layer

Agent 1

Reactive SOP Matcher

  • Listening for correlated high/critical alarms only
  • Enriches from 4 data sources using semantic search and structured retrieval:
    • equipment_registry
    • plant_sops
    • incident_history
    • automation_policies
  • Calls the LLM with tool_use → structured action plan (not free text)
  • Writes to action_queue with per-policy approval mode
Agent 2

Trend Analysis

  • Sliding-window aggregation on sensor_telemetry via $setWindowFields
  • Rolling $derivative + $avg over 30 s
  • Fires predictive warnings before thresholds trip
  • Operators get a head start on the hard alarm
Agent 3

Alarm Correlator

  • Change-stream on plant_alarms
  • 5 s debounce by root-cause group
  • Equipment dependency traversal
  • One group → one diagnosis → one remediation
Agent 4

Production Monitor

  • Plan vs actual comparison every 15 s
  • Deviation + projected finish, live
  • Closes resolved events; freezes final deviation

Human-in-the-loop, by data

Every proposed setpoint change hits the action_queue with a state machine:

proposed → approved → executing → completed

The automation_policies collection decides whether an action runs autonomously or needs sign-off — per action type, per area, per subsystem.

  • Emergency steam shutoff → autonomous (waiting is the risk)
  • Pump speed change → human approval
  • Valve override → human approval

Trust is dialled up by editing data, not by shipping new agent code.

What the operator sees

  • Diagnosis in plain language
  • Setpoint changes with SOP step references
  • Historical context ("last 2 times, resolved in ~90s")
  • Severity + confidence
  • One click: Approve & Execute or Reject

Section Two

Why MongoDB Atlas

One platform. Time series, vectors, change streams, documents — no stitching.

Native Time Series collections

Plant telemetry is the canonical time-series workload — thousands of tags at 1–5s granularity, 24/7.

  • Purpose-built storage — columnar compression per time bucket; 10×+ smaller than row-oriented
  • Automatic bucketing — no app-side rollups to maintain
  • Window aggregations — $setWindowFields for sliding-window trend detection
  • TTL & tiering — hot/warm/cold lifecycle out of the box
  • Same query surface — same drivers, same aggregation framework, same cluster
db.createCollection(
  "sensor_telemetry",
  { timeseries: {
      timeField: "ts",
      metaField: "tag",
      granularity: "seconds" } }
)

// Agent 2's drift detection
db.sensor_telemetry.aggregate([
  { $match: { tag: "M3MX3.CHARGEFL",
              ts: { $gte: windowStart }}},
  { $setWindowFields: {
      sortBy: { ts: 1 },
      output: { slope: {
        $linearFill: "$value" }}}}
])

Automated Embeddings with Voyage AI

Zero client-side embedding code. Atlas calls Voyage AI's voyage-4-large model for you — on insert and on query.

  • No embedding service to deploy, scale, monitor, or secure
  • No dimension / model-version drift — Atlas keeps the index in sync
  • Query with plain text — {"text": "dosing flow collapsing"}, Atlas embeds it on the fly
  • Best-in-class retrieval — Voyage models consistently top MTEB benchmarks for enterprise RAG
  • Same cluster, same auth — vectors live beside the operational data they describe
// Index definition — one block, no services
{
  "fields": [{
    "type": "vector",
    "path": "content_embedding",
    "model": "voyage-4-large",
    "modality": "text",
    "autoEmbed": true
  }]
}

// Query from Agent 1 — plain text, no vectors
db.plant_sops.aggregate([{
  $vectorSearch: {
    index: "sop_auto_vector_index",
    path: "content_embedding",
    query: { text: "water dosing starvation,
                    flow collapsing, valve
                    opening to compensate" },
    numCandidates: 20,
    limit: 3
}}])

Change Streams — the database is the event bus

Agents react to new alarms and groups in real time, with no Kafka, no RabbitMQ, no polling loop.

  • Agent 3 watches plant_alarms
  • Agent 1 watches correlated_alarm_groups
  • Resumable tokens guarantee at-least-once delivery across restarts
  • Filtered server-side with $match — only the events each agent cares about
  • One less piece of infrastructure to run, secure, and page on
pipeline = [{"$match": {
    "operationType": "insert"
}}]
with db.plant_alarms.watch(pipeline) as stream:
    for change in stream:
        alarm = change["fullDocument"]
        correlate(alarm)   # debounced
        # resume token stored for crash safety
"MongoDB is both the database and the event bus."
